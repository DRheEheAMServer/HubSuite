# 客户端模组（双端）架构说明

> 本文记录 `hubsuite` 与 `hubsuite-client` 双端配套架构、分工与兼容机制。
> 兼容与发版规则见 [客户端契约](客户端契约.md)、[分发与更新](分发与更新.md)。

## 1. 架构决策

| 决策 | 选择 | 影响 |
|---|---|---|
| 模组形态 | **两个独立模组**（`hubsuite` + `hubsuite-client`） | 两份产物、**版本各自独立**（客户端只在真改动时递增） |
| 兼容策略 | **强制安装** | 两端注册表直接同步对齐；未装客户端在注册表同步阶段即断开 |
| 客户端负责范围 | **表现层**（真物品注册 + 分层渲染 + 自定义界面 + 岩浆浮标同步渲染） | 服务端无需 Polymer，无需下发资源包 |
| 部件外观 | **运行时逐层渲染** | 杆 / 线 / 钩 / 升级 / 破损裂纹组合渲染 |
| 资源包 | **内置于客户端模组** | 统一放在 `common/resources/` 与 `client/src/main/resources/` |
| 版本绑定 | **硬门槛 + 软区间** | 注册表保证同协议接入，`clientCompat` 校验最低版本号 |

## 2. 目录结构

```text
仓库（同一仓库，多项目 Gradle）
├─ 根项目 = hubsuite（服务端模组）
│   └─ gradle.properties: server_version / client_version
├─ common/ = 双端共用源码与素材（物品定义、网络负载、钓竿规则、布局、语言文件）
└─ client/ = hubsuite-client（Fabric 客户端模组）
    ├─ 注册与服务端一致的物品、方块与菜单类型
    ├─ 运行时分层物品渲染与 Tooltip
    ├─ 装配台自定义容器界面（HubSuiteContainerScreen）
    └─ 客户端岩浆浮标同步与渲染 Mixin
```

- **版本**：`server_version` 与 `client_version` 各自独立；服务端不依赖客户端模组。
- **握手校验**：玩家登录后服务端通过 `ClientCompat` 发送自定义 payload，客户端回传版本号、协议号、指纹与能力清单（`real_items_v1`）。
- **玩法权威性**：客户端模组**只做表现层**（渲染 / 界面 / 动效），所有判定（属性、消耗、断线、附魔、岩浆钓鱼裁决）均在服务端完成。

## 3. 代价与风险（选型的直接后果）

1. **必须装客户端**这一条长期不变；但「每次都要跟着更新」已用硬门槛 + 软区间消掉（旧客户端进得来、只是缺新表现）—— 剩下的成本转移到分发与更新上（见[分发与更新](分发与更新.md)）。以下是已解决的原始描述（留档）：这是"强制安装 + 严格同版本" 的必然代价。
2. **去掉 Polymer 后没有兜底**：客户端不装或版本不符时看到的是未知物品/缺失模型（这正是"强制"的含义）；迁移期间靠"Polymer 与真物品并存"过渡；
3. **物品注册方式迁移**：现在所有自定义物品都靠 Polymer 映射成原版物品；改成真物品要逐个过一遍（地狱线、三种渔桶、以及钓竿系统的部件），并重做物品显示；
4. **资源包下线**：素材要从"服务端 jar + Polymer 下发"改成"客户端模组内置"，仓库里要重新组织素材位置（现有 `src/main/resources/assets/hubsuite/**` 会拆成服务端/客户端两份或共用）；
5. **测试缺口**：服务端自检（现有 253 项）覆盖不到客户端渲染与界面 → 每轮都要实机看（你那边验收 + 我这边 `runClient`）；
6. **分发**：渠道已定 = GitHub Release 双产物 + 群文件/网盘镜像，自动更新按需推进（见[分发与更新](分发与更新.md)）；

## 4. 工作量分解

| 工作项 | 估算 |
|---|---|
| 多项目 Gradle 改造（根保持服务端 + `client/` 子项目 + 共享版本） | 0.5~1 天 |
| 客户端模组骨架（entrypoint、物品注册同步、开发用 `runClient`） | 0.5 天 |
| 最小数据契约（钓竿组件 + 部件物品注册，服务端与客户端一致） | 0.5 天（与钓竿系统第 1 步共用） |
| 运行时分层物品渲染器（含缓存） | 1~2 天 |
| 装配台自定义 Menu + Screen + 美术 | 1~2 天 |
| Polymer → 真物品迁移（现有物品逐个过） | 1~2 天 |
| 资源包下线 + 素材整理 | 0.5 天 |
| 客户端契约 v1（只增不改纪律 + 未知即占位 + 黄金字节测试 + 版本/指纹上报） | 0.5 天 |
| 服务端握手（版本 + 能力 + 指纹） | 0.5 天 |
| 每轮客户端实机回归 | 0.5 天/轮 |
| **合计** | **约 6~9 个工作日（≈ 9~13 轮提交）** |

## 5. 与钓竿系统的衔接（顺序）

1. **契约先行**：客户端契约 v1（只增不改 / 未知即占位 / 握手 / 黄金字节测试）→ 再定钓竿的组件结构（部件 / 升级 / 耐久 ×10）并实现最小版本（只做注册与读写，不做玩法）；
2. **客户端渲染**：分层渲染器读该组件 → 杆 / 线 / 钩 / 升级逐层画；
3. **客户端界面**：装配台自定义菜单与界面（不再受"借壳换皮"限制，也没有副作用）；
4. **服务端玩法**：属性公式、材料消耗、修补/换底、铁砧升级、断线、青金石附魔（全部按[钓竿系统方案](钓竿系统方案.md)）；
5. **清理**：删掉借壳菜单与换皮方案、去掉 Polymer 依赖、关掉资源包下发；
6. **收尾**：握手校验（强制安装）+ 文档与安装说明更新。

> 注意：第 2、3 步虽然"先做"，但依赖第 1 步的组件契约 —— 不能真的"零服务端"起步。

## 6. 决策回顾（为什么不能既要又要）

- 运行时逐层渲染 + 自定义界面 → 必须有客户端模组；
- 客户端模组一旦"强制"，原版客户端就不再是目标 → **资源包与 Polymer 映射也就失去意义**，可以下线；
- 反之若哪天想回到"原版客户端也能玩"，就必须保留 Polymer + 资源包 + 借壳界面那一整套 fallback（成本翻倍）。**当前选型是彻底放弃原版客户端兼容**。

## 7. 已定与待定

**已定（2026-10）**

1. **分发渠道**：GitHub Release 双产物 + 群文件/网盘镜像；**不上 Modrinth / CurseForge**（平台规则限制，且私有服专用模组上架无收益）；
2. **过渡期**：**直接切强制安装**，不设"装了才有新外观"的过渡版；
3. **握手失败行为**：分三档 —— 没装或低于 `MIN_CLIENT` → 踢出并给下载地址；兼容区间内 → 放进来按能力降级；≥ 推荐版本 → 全功能（见[客户端契约](客户端契约.md)第 5 节）。

**待定**

- **通用容器界面**：服务端给槽位布局、客户端通用渲染（约 +1 天）。建议做；不做则每个新界面 = 一次客户端小版本。见[客户端契约](客户端契约.md)第 8 节。
